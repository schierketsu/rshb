# 7. Ожидаемый эффект и план внедрения

## 7.1. Ожидаемый эффект

| Показатель | Сейчас (оценка) | После интеграции (цель) | За счёт чего |
|---|---|---|---|
| Время обнаружения сбоя (MTTD) | 15–40 мин — после звонка пользователя | **≤ 2 мин** | опрос 30 с + push в «Диво» |
| Доля инцидентов казначейства, зарегистрированных автоматически | ≈ 0 % | **≥ 80 %** | события → правила → инцидент |
| Время восстановления (MTTR) | — | **−20–30 %** | инцидент сразу содержит операцию, КЕ, код ошибки, инструкцию |
| Полнота SLA-отчётности | только сбои, о которых сообщили | **100 % сбоев**, точное время начала и конца | пара FIRING/RESOLVED |
| Обращения в поддержку во время известного сбоя | каждый пострадавший звонит | **−50 %** | виджет «Известная проблема» на портале |
| Срывы расчётов по причине ИТ | — | снижение | реакция до cut-off платёжных систем |
| Время дежурного на ручную регистрацию | 5–10 мин на инцидент | **0** | автоматическое создание |

> Значения «сейчас» — экспертная оценка типичной ручной схемы, а не данные банка.
> Целевые значения предлагается зафиксировать как KPI пилота и измерять в «Диво Мера»:
> MTTD = `detectedAt − occurredAt` + время до создания инцидента; доля автоинцидентов — по источнику.

**Качественный эффект**
* Бэк-офис казначейства перестаёт быть «системой мониторинга» для ИТ.
* Владелец услуги получает объективные данные о доступности для разговора с вендором и бизнесом.
* Статистика причин показывает, какие узлы Treasury.Back дорабатывать в первую очередь.
* Решение **тиражируется**: адаптер + контракт событий подходят для других систем на Diasoft FA#
  и других бэк-офисных систем банка — меняются только Source Connectors и правила.

## 7.2. План внедрения

| Этап | Срок | Результат |
|---|---|---|
| 0. Согласование | 2 нед. | утверждённый каталог событий, нормативы, коды услуг и КЕ в CMDB, доступ к реплике |
| 1. MVP | 4–6 нед. | адаптер: опрос реплики + health-probe, 4 события (`OPERATION_DELAYED`, `SETTLEMENT_REJECTED`, `EOD_CLOSE_DELAYED`, `SYSTEM_UNAVAILABLE`); `/events`, `/heartbeat`; экран мониторинга |
| 2. Пилот (теневой режим) | 4 нед. | события идут в «Диво», инциденты не создаются; настройка порогов по реальным данным, сверка с ручными обращениями |
| 3. Промышленная эксплуатация | 2 нед. | автоинциденты, SLA-таймеры, карточка события, виджет портала |
| 4. Развитие | далее | `/metrics` и дашборд «Мера», остальные события, тиражирование на другие системы, при росте объёма — переход на брокер сообщений |

**Почему теневой режим:** неверно настроенные пороги — главный риск мониторинга («шторм» ложных
инцидентов). Месяц наблюдения без создания инцидентов позволяет откалибровать нормативы.

## 7.3. Риски и меры

| Риск | Мера |
|---|---|
| Ложные срабатывания, «шторм» инцидентов | теневой режим, группировка по `correlationKey`, пороги инцидента, подавление при аварии |
| Нагрузка на БД казначейства | только read-only реплика, индексированные запросы, опрос 30 с |
| Изменение структуры БД при обновлении Diasoft | запросы вынесены в Source Connector; регрессионные тесты при обновлении |
| Потеря событий | outbox, повторы, DLQ, heartbeat |
| Утечка чувствительных данных | минимизация полей, `additionalProperties: false`, mTLS, аудит |
